workshop.

Imagine a little workshop where you ask for help, helpers do jobs, and a notebook keeps your work. You’ll build it one working piece at a time.

A plan, not a finished app

A home for helpers that can do jobs.

Your documents describe a Mac app where you can keep projects, talk to Chief, and eventually let specialist bots work together.

Think of building with toy blocks. You choose what to make. Chief helps organize the job. The harness supplies the workspace, the tools, and the rules.

THE HELPER’S LANGUAGE SKILL

AI model

A system that produces responses from the information you give it. Later, your app connects to an existing model or supported agent service. You don’t have to train your own model.

THE WORKSHOP

Harness

The software around the AI: it passes along messages, supplies allowed tools, saves work, checks results, and decides when to stop or ask you.

THE HELPER AT WORK

Agent

An AI-powered helper working toward a goal, with instructions and permitted tools. Chief is the lead role; specialist bots have smaller jobs.

Your first version has a pretend helper.

“Mock Chief” gives a programmed reply. It does not think, call a model, or do real work. That lets you test the workshop without needing AI credentials or spending model tokens.

“Saved” does not mean “learned.”

Keeping chat history is like putting pages in a notebook. Later memory features would choose useful lessons and bring them into future work. Neither action automatically retrains the model.

Where do bots, memory, and Git fit?

Bots divide jobs. A durable bot keeps its identity and settings; a temporary worker lasts for a task. Persistence does not mean it is always running.

Memory supplies relevant notes, with separate user, bot, and project scopes. Users should be able to inspect, edit, and delete those notes.

Git worktrees give coding bots separate copies of a Git project to work in. Chief reviews integration; separate copies can still have conflicting changes.

Remote workers could run jobs when your laptop is closed. Local work needs a computer that is on and able to run it.

Recommended working order

Build one small thing. Prove it works.

The full idea is too much for one beginner-sized task. Keep the big vision, but work on one visible behavior at a time. These are work slices, not promises about how many days they take.

Your very first win

Open a desktop window. See the sidebar. See “Python connected.” Stop Python and see “Disconnected” instead of a crash.

That is task 1. A working, saved mock chat is the larger milestone 1. Task 1 does not need a database or a real model yet.

Start with this learning question:

“When I press a button on the screen, how can Python hear about it and send something back?”

Open the app and connect Python

Build: A Mac window, Projects home, and the persistent sidebar. Electron starts/stops Python. The health endpoint answers “I’m here.” Future tabs are labeled as placeholders.

Learn: A process is a running program. A request is a question sent to another program. A response is its answer.

Done when: The app opens, shows connected, and handles a stopped backend without crashing. A backend health test and a frontend smoke test pass. Setup instructions work.

Your practice: Explain the connection in your own words, then deliberately stop Python and observe the error state. Keep local access restricted from the start.

Give the app a notebook

Build: A SQLite database for projects, sessions, and messages. Give each record a unique ID. Add a migration: a recorded change to the database’s structure.

Learn: A table is like a list with named columns. IDs connect one list to another. A project ID on a session can be empty.

Done when: A test can save a record, close the database connection, reopen it, and read the same record. Use the app’s data folder, not the Git repository.

Register one project folder

Build: Choose an existing folder through a controlled picker. Python checks access and saves a project record. Show it on Projects home.

Learn: A path is a folder’s address. A project’s ID is its identity; these are different things.

Done when: A chosen folder appears after restart; an inaccessible folder produces a useful error. Registering a folder does not trigger a deep scan.

Your practice: Implement one small endpoint and its test with help as needed. Explain what it accepts and returns.

Create two kinds of chat

Build: One session inside a project and one standalone session. Reopen each from the interface.

Learn: Optional relationships: a chat may belong to a project, but it does not have to.

Done when: Both sessions survive restart, and opening one shows the correct conversation rather than the other session’s messages.

Send a message to pretend Chief

Build: Send text, get a predictable programmed reply, and save both messages. Show waiting and failure states.

Learn: Trace the whole trip: screen → Python → storage → reply → screen.

Done when: You send a message, receive a mock reply, close the app, reopen the session, and see both in the right order. No model account is needed.

Make the small version dependable

Build: Clear empty/error states, honest placeholder labels, readable setup instructions, and focused tests for the behaviors above. Write a plan for bundling Python with a future distributable app.

Learn: A feature is finished when you can demonstrate it and explain its limits.

Done when: You can repeat the launch → register folder → open both chat types → send → restart demo. Tests pass. Local access protections are checked. Document packaging limits honestly.

Your practice: Debug one failure, review each change before merging, and write three lines: “I built… I learned… Next I’ll…”

How to use AI while you learn

1. Predict

Say what you expect the feature to do.

2. Take one step

Ask for an explanation or hint. Ask for code when you want it.

3. Prove it

Run it yourself. Try one failure case too.

4. Explain it

Describe each piece without reading the answer.

A useful tutoring request

“Help me understand task 1. Explain one piece at a time. Let me predict what happens. Give me a small hint before a solution, and only give me code when I ask.”

What comes after milestone 1?

This follows ROADMAP.md. Move on when the previous part works, not just because the next idea is exciting.

  1. One real provider: verify an official integration and its authentication first. Don’t assume a subscription includes API access.
  2. Chief and saved bots: roles, identity, and task records.
  3. Tools and controls: permissions, steer, queue, pause, and resume.
  4. Teamwork and checking: bot messages, tests, evidence, and Chief review.
  5. Memory: retrieve useful notes and test whether they help.
  6. GitHub and editor: worktrees, pull requests, and code editing.
  7. Background work: schedules, events, budgets, and remote workers.
  8. Mobile and multiple users: remote access and separation of each user’s data.

Big words, small meanings.

You do not need to learn this whole list before starting. Look up a word when it appears in the piece you’re building.

Frontend / backend
The part you see and touch / the part handling requests and data behind it.
In this plan: React / Python.
Electron
The desktop container that puts your interface in a Mac app window and manages the local Python program.
A proposed choice, not a claim about Codex’s internals.
React
Builds the screen from reusable pieces, such as a message bubble or project list.
TypeScript
JavaScript with checks that help you catch some mistakes before you run the app.
Used for the desktop/interface code.
Vite / Tailwind CSS
Vite helps run and build the frontend. Tailwind helps style how the interface looks.
Python / FastAPI / Pydantic
Python is the language. FastAPI gives the backend request routes. Pydantic helps check the shape of incoming information.
API / endpoint / HTTP
An API is a set of ways programs talk. An endpoint is one place to ask for something. HTTP is the request-and-response language used here.
Example: GET /health asks “Are you running?”
SQLite / persistence
SQLite keeps structured data in a local database file. Persistence means the information survives closing the app.
Mock / test
A mock is a pretend part with predictable behavior. A test checks whether a piece does what you expected.
pytest tests Python; Vitest tests frontend code; React Testing Library helps test UI behavior.
CRUD / schema / migration
CRUD means create, read, update, delete. A schema describes stored data. A migration records how that structure changes.
The first screens need only their planned operations; don’t add every CRUD action automatically.
Provider / adapter
A provider supplies AI capability. An adapter translates your app’s requests into the way a supported provider expects them.
Later. Capabilities and official sign-in options need verification.
Localhost / permissions
Localhost means this computer. Permissions define what a helper is allowed to do. Being local does not prove which program is making a request.
Use restricted local access and a narrow bridge to desktop capabilities.
Tokens / budget
Tokens are chunks of information a model processes. A budget sets limits on how much work, time, or spending a task can use.
Worktree / pull request
A worktree is a separate working copy of a Git repository. A pull request is a proposed set of changes to review before combining them.
Git workflows are a later stage in this plan.

Three details to reconcile before implementation

Bot timing: The technical spec mentions bot persistence in milestone 2, but the roadmap puts providers in stage 2 and bots in stage 3. This guide follows the roadmap; both defer real bots beyond milestone 1.

Local access protection: Architecture says to plan authentication before privileged actions; the technical spec calls for an app-scoped secret or protected local communication in milestone 1. Follow the stricter baseline while choosing the concrete design.

Field names: The files use both “display_name / local_path” and “name / workspace_path.” Choose one naming scheme before implementing storage. The underlying ideas are the same.

Still proposed: The stack and packaging approach need validation. This guide explains the supplied plan; it does not confirm current provider support or report an implemented app.
